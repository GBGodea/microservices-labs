# ADR-002. PostgreSQL как хранилище по умолчанию и исключения из этого правила

**Статус:** Принято.  
**Дата:** 2026-11-05.  
**Система:** платформа аренды электросамокатов, вариант 2224.

Подробное обоснование, индексы, партиционирование, шардирование и эксплуатация описаны в [«Хранении данных»](../data-storage.md). Этот ADR фиксирует само решение и условия его пересмотра.

## Контекст проблемы

[ADR-001](ADR-001-decomposition.md) разделил систему на сервисы с собственными хранилищами: прямой доступ к чужой БД запрещён. Нужно решить, какую СУБД получает каждый сервис и почему, а не выбирать «по привычке».

Требования к хранению (подробно — [§1](../data-storage.md#1-требования-к-хранению-вытекающие-из-архитектуры)):

- **Инварианты «не более одного»:** одна незавершённая поездка пользователя, один владелец самоката (lease + fencing token), одна денежная операция на бизнес-ключ, один штраф на свидетельство и версию политики. Нужны уникальные ограничения в той же транзакции, что и изменение.
- **Transactional outbox, inbox и идемпотентность** во всех сервисах-производителях; публикация событий через CDC из WAL (Debezium), без двойной записи «БД + брокер».
- **Durable saga** старта и завершения поездки и очереди повторов в Billing, Fleet, Photo с конкурирующими worker'ами.
- **Неизменяемые snapshot:** версии тарифов и геозон, котировки, подписанные измерения.
- **Гео:** полигоны версий геозон; быстрый поиск самокатов рядом (~3 250 RPS, 65 % пика).
- **Объёмы (условно, A1–A6):** ~1 млн поездок/сут, ~1,1 ТБ/год поездок; ~4 млн проводок/сут; до ≈ 20 тыс. штрафов/сут (верхняя оценка, A6); 20 000 измерений телеметрии/с (~170 ГБ/сут сырых); ~0,4 ТБ/сут фото (≈ 46 ТБ оригиналов в установившемся режиме вместе с фото повреждений, обжалований и удержанными по штрафам, ≈ 50 ТБ объектов вместе с производными — [§4.2](../data-storage.md#42-объёмы-и-эксплуатационные-параметры-условно); 250 фото/с ≈ 100 МБ/с — проектная цель с запасом ≈ ×9 к среднему пикового часа ≈ 28 фото/с); финансовые записи ≥ 5 лет (402-ФЗ).
- **Надёжность:** SLO 99,95 %, RPO ≈ 0 для Trip, Fleet, Billing, PITR.
- **Ограничения:** ПДн граждан РФ — в БД на территории РФ (152-ФЗ); лицензия и managed-предложения должны быть доступны в РФ; эксплуатирует одна команда DevOps.

## Рассмотренные альтернативы

| Вариант | Описание | Преимущества | Недостатки и решение |
| --- | --- | --- | --- |
| 1. PostgreSQL для всех OLTP-сервисов + расширения + специализированные хранилища для неподходящих данных | PostgreSQL на сервис; PostGIS для Geofence; TimescaleDB для Telemetry; Redis — производная проекция Discovery; S3 — бинарные фото; Kafka — события | ACID, UNIQUE, частичные индексы, EXCLUDE, `SKIP LOCKED`, JSONB, logical replication для Debezium; один стек на 8 БД; разрешительная лицензия; managed в РФ | Масштабирование записи — вертикальное, шардирование в приложении; сжатие и continuous aggregates TimescaleDB — под Timescale License (TSL): self-managed эксплуатация разрешена, но у managed-провайдера полной редакции может не быть. **Выбрано** |
| 2. MySQL 8 / MariaDB | Реляционная СУБД для OLTP, Vitess для шардирования | ACID, `SKIP LOCKED`, зрелое шардирование (Vitess) | Нет частичных индексов и EXCLUDE, нетранзакционный DDL, слабее гео, нет аналога TimescaleDB → для гео и телеметрии понадобился бы второй стек. Отклонено |
| 3. MongoDB | Документная СУБД с встроенным шардированием | Гибкая схема, 2dsphere, шардирование из коробки | Многодокументные транзакции дороже, учёт и сверки неестественны; SSPL; Atlas в РФ недоступен. Отклонено |
| 4. Cassandra / ScyllaDB | Wide-column, линейная запись | Очень высокая скорость записи, TTL | Нет транзакций и уникальности, кроме PK; не выражает инварианты. Отклонено для OLTP; кандидат для сырой телеметрии при росте ×10 |
| 5. CockroachDB / YugabyteDB | Distributed SQL | Распределённые ACID, авто-шардирование, multi-region | Консенсус на каждый коммит (задержка); горячая строка всё равно сериализуется; новый стек; CockroachDB — проприетарная лицензия; managed в РФ нет. Отклонено до появления multi-region active-active |
| 6. Redis как основное хранилище | In-memory | Минимальная задержка, GEO-команды | Нет отката транзакций; асинхронная репликация теряет подтверждённые записи при failover. Только для производной проекции |
| 7. ClickHouse | Колоночная аналитическая СУБД | Сжатие, агрегаты по истории | Нет OLTP-транзакций и уникальности. Только DWH и, возможно, история телеметрии |

Таблица по критериям (транзакции, гео, временные ряды, масштабирование, эксплуатация, лицензия) — в [§3](../data-storage.md#3-сравнение-альтернатив).

## Выбранное решение

1. **PostgreSQL — хранилище по умолчанию** для всех сервисов, владеющих источником истины: User, Fleet, Trip, Pricing, Billing, Geofence, Photo (метаданные), Telemetry. Каждый сервис — отдельная логическая БД со своей учётной записью и миграциями; межсервисные запросы и FK запрещены даже на общем кластере.
2. **Расширения вместо отдельных СУБД:** PostGIS в `Geofence DB`, TimescaleDB в `Telemetry DB`. Если провайдер не даёт полную редакцию TimescaleDB, `Telemetry DB` — self-managed кластер Patroni.
   - **Лицензия TimescaleDB.** Сжатие, continuous aggregates и фоновые политики — функции Timescale License (TSL). TSL запрещает только предоставлять TimescaleDB третьим лицам как сервис (DBaaS); собственная self-managed эксплуатация для своего продукта разрешена. Мы DBaaS не предоставляем, поэтому TSL допустима.
   - **Запасной вариант без TSL** (если изменятся лицензия или провайдер): нативное декларативное партиционирование `telemetry_measurement` + BRIN по времени измерения + `pg_partman` для создания и удаления партиций; минутные агрегаты строит job, а не continuous aggregate. Цена — больший диск без сжатия, а не смена СУБД ([§2.2](../data-storage.md#22-версия-и-расширения)).
3. **Исключения, где PostgreSQL структурно не подходит:**
   - `Discovery Index` — Redis Cluster: производная восстановимая GEO-проекция; источник истины остаётся у владельцев.
   - Бинарные фото — S3-совместимое объектное хранилище; в `Photo DB` — только метаданные и статус.
   - Доменные события — Kafka; первичная запись события — outbox в БД производителя.
   - Данные старше горячего окна — платформенное архивное хранилище `Archive Store`: Parquet в S3-совместимом объектном хранилище в РФ с versioning и Object Lock (Trip — 5 лет; Billing — compliance ≈ 6 лет, 402-ФЗ), владелец — платформа DevOps ([§6.4](../data-storage.md#64-архивирование-detach--parquet--drop)); аналитика — DWH (ClickHouse) вне рамок лабораторной.
4. **Общие приёмы для всех БД** (подробно — [§5–8](../data-storage.md#5-индексы)):
   - PK — UUIDv7.
   - Инварианты — в маленьких непартиционированных таблицах (`user_active_trip`, `scooter_active_lease`). Уникальный ключ партиционированной таблицы включает ключ партиционирования; бизнес-ключ, который не может его включить, живёт в непартиционированной таблице (`fine`, `psp_webhook_inbox`) — [§5.2](../data-storage.md#52-инварианты-отдельные-непартиционированные-таблицы-и-частичные-уникальные-индексы).
   - Очереди — частичный индекс + `FOR UPDATE SKIP LOCKED`.
   - Крупные таблицы — помесячное партиционирование `RANGE` по UUIDv7 с архивом в Parquet (`Archive Store`).
5. **Шардирование не включается, но модель shard-ready:** 256 логических бакетов, карта «бакет → кластер», маршрутизация в приложении. Ключи: Trip и Billing — `userId`, Fleet — `cityId`, Telemetry — `scooterId`. Сервис, создающий ID, записывает бакет в последний байт UUIDv7: `tripId` и ID Billing — бакет `userId`, `leaseId` и `commandId` — бакет `cityId` (`commandId` генерирует Trip и копирует последний байт `leaseId`, Fleet это проверяет), `photoId` — бакет владельца, `checkId` и `evidenceId` Geofence — бакет `cityId`. Запрос по ID маршрутизируется без справочника и без опроса всех кластеров ([§7.3](../data-storage.md#73-shard-ready-модель)).
6. **HA:**
   - Trip, Fleet, Billing — синхронная реплика в другой AZ (RPO ≈ 0) и асинхронная read replica.
   - Остальные БД (кластер `pg-core`: User, Pricing, Geofence, Photo) — асинхронная по умолчанию; кворумная синхронная реплика настроена (`synchronous_standby_names = 'ANY 1 (replica)'`, по умолчанию `synchronous_commit = local`), критичные транзакции поднимают `SET LOCAL synchronous_commit = on` (User — блокировки, удаление, ротация ключей; Pricing — админские изменения тарифов; Geofence — запись свидетельств, опционально) ([§8.2](../data-storage.md#82-ha-patroni-или-managed)).
   - Telemetry — асинхронная реплика: потеря секунд истории допустима.
   - PgBouncer (transaction pooling) перед каждой БД.
   - pgBackRest/WAL-G с PITR и ежемесячной проверкой восстановления. Окно PITR: Billing — 35 сут; User — 14 сут (152-ФЗ; после восстановления обезличивание выполняется повторно); Telemetry — 7 сут; остальные — 14 сут ([§8.5](../data-storage.md#85-бэкапы-и-pitr)).
   - Ограничение WAL для слотов Debezium.

## Обоснование выбора

1. **Инварианты держит СУБД, а не приложение.** Уникальные ограничения и условные обновления в одной транзакции исключают гонки «проверил — вставил» для поездки, lease и денежных операций. Это прямо закрывает проблемы двойной аренды и двойного списания из [отчёта](../lab-01.md).
2. **Outbox без двойной записи.** Изменение агрегата и событие коммитятся вместе, а Debezium читает их из WAL через встроенный `pgoutput`. Отдельный relay в каждом сервисе не нужен.
3. **Один стек на 8 из 9 сервисов.** Гео и временные ряды покрываются расширениями. У команды одни инструменты HA, бэкапа, мониторинга, миграций и CDC вместо трёх СУБД.
4. **Объёмы помещаются в один primary на сервис.** По оценкам горячие данные PostgreSQL — ~5–6 ТБ на 8 БД; крупнейшая — Billing ~1,7 ТБ, за ней Trip ~1,2–1,3 ТБ. Партиционирование и архив держат их стабильными. Распределённая СУБД решала бы отсутствующую пока проблему ценой задержки каждого коммита.
5. **Лицензия и доступность.** PostgreSQL License разрешительная; managed PostgreSQL есть у провайдеров в РФ; Postgres Pro есть в реестре российского ПО. Это снижает лицензионные и санкционные риски.
6. **Исключения обоснованы природой данных, а не удобством.** В Redis — только то, что можно перестроить. В объектном хранилище — то, что раздуло бы WAL и бэкапы в сотни раз. Kafka — журнал, а не источник истины.

## Положительные последствия

- Инварианты, идемпотентность и outbox реализуются одинаково во всех сервисах; общая библиотека и единые ревью DDL.
- Debezium Outbox Event Router работает поверх всех БД без изменений в сервисах.
- Синхронная репликация и PITR дают RPO ≈ 0 для критичных сервисов на стандартных инструментах.
- Рост объёма решается партиционированием и архивом без изменения кода; рост записи — заранее подготовленным шардированием по бакетам.
- Отказ Redis, Kafka или объектного хранилища не теряет бизнес-фактов: их источник истины — в PostgreSQL.

## Отрицательные последствия и ограничения

- **Масштабирование записи** одного сервиса упирается в один primary до включения шардирования. Шардирование в приложении — собственный код маршрутизации и процедур переноса бакетов.
- **Ограничения партиционирования:** уникальность обязана включать ключ партиции. Отсюда отдельные таблицы инвариантов и реестры бизнес-ключей, а запросы без ключа сканируют все партиции.
- **Синхронная реплика** добавляет межзонную задержку к каждому коммиту Trip, Fleet, Billing. При потере обеих реплик Billing останавливает запись (осознанный выбор).
- **Риски эксплуатации:**
  - Logical-слоты Debezium могут удерживать WAL и заполнить диск, поэтому нужны `max_slot_wal_keep_size` и мониторинг.
  - Transaction pooling запрещает сессионное состояние.
- **TimescaleDB:** сжатие и continuous aggregates распространяются под Timescale License. Для нас она допустима (self-managed эксплуатация, DBaaS не предоставляем), но означает зависимость от self-managed кластера или провайдера с полной редакцией. Запасной вариант без TSL (нативное партиционирование + BRIN + `pg_partman`) снимает привязку ценой большего диска.
- **Межсервисная и межшардовая аналитика** невозможна в OLTP и требует отдельного DWH.

## Как проверить и когда пересмотреть

Проверка:
- Нагрузочный тест на профиле A1–A2 с запасом. Цели: загрузка записи primary < 60 %; p99 транзакции старта поездки в целевых границах; лаг слота Debezium < 10 с.
- Ежемесячное автоматическое восстановление бэкапа с PITR: фактический RTO не выше целевого ([§8.6](../data-storage.md#86-цели-rporto-проектные)).
- Учение failover: RPO = 0 для Trip, Fleet, Billing; Debezium продолжает публикацию без потерь.
- Тест на конкурентный старт: два параллельных старта одного пользователя и аренда одного самоката двумя пользователями дают ровно одну успешную операцию.

Пересмотреть решение, если:
- **Телеметрия выросла ×10** (≈ 200 000 изм./с). Первым шагом — шардирование `Telemetry DB` по `scooterId`. Если этого мало: ClickHouse для истории или ScyllaDB/Cassandra для ключевого доступа с TTL.
- **Триггеры шардирования** ([§7.2](../data-storage.md#72-триггеры)) достигнуты в нескольких сервисах и маршрутизация в приложении стала дорогой → Citus для Trip и Billing.
- **Появилось требование multi-region active-active** с RPO = 0 при потере региона → региональные ячейки по `cityId`; при недостаточности — YugabyteDB/CockroachDB для Trip и Fleet.
- **Провайдер в РФ не поддерживает** нужные расширения или версию PostgreSQL → self-managed кластеры Patroni для соответствующих БД.
- **Изменились лицензионные условия** PostgreSQL-расширений, Redis или Kafka → пересмотр соответствующего исключения (например, Valkey вместо Redis).
